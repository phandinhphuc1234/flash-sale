# Implementation Plan: Seckill Observability Baseline

**Branch**: `codex/phase25-seckill-observability` | **Date**: 2026-08-28 | **Spec**: [spec.md](spec.md)

**Input**: Approved feature specification from `specs/045-seckill-observability/spec.md`

## Summary

Deploy a deliberately small, internal-only Prometheus and Grafana stack on the existing EKS cluster.
Prometheus scrapes the eight Spring Boot services through stable Kubernetes DNS and loads the
existing seckill/Saga alert rules. Grafana provisions one datasource and one Seckill Overview
dashboard from Git. A dedicated Argo CD Application owns `infra/monitoring`; a bounded PowerShell
runner validates, installs, and verifies the stack without printing credentials. Slack,
Alertmanager, Loki, Tempo, exporters, public ingress, and application-code changes are deferred.

## Design Decisions

### D1 — Plain Prometheus and Grafana manifests

Use two Deployments and two ClusterIP Services rather than Helm or Prometheus Operator. This avoids
CRDs, RBAC discovery, chart complexity, and another package manager for a small internship cluster.

### D2 — Static Kubernetes DNS scrape targets

Prometheus scrapes eight stable Service DNS names. The project intentionally runs one replica per
service, so static targets are sufficient and require no cluster-wide discovery permission.

### D3 — Git-provisioned disposable UI state

The datasource, dashboard, rules, and Prometheus config are ConfigMaps generated by Kustomize.
Prometheus and Grafana use `emptyDir`; a restart can discard history or local UI edits. This is an
explicit demo trade-off and keeps the stack small and recoverable from Git.

### D4 — Separate Argo ownership

`flash-sale-observability` owns only `infra/monitoring`. It is separate from `flash-sale-cloud`, so a
monitoring failure cannot block or prune application resources. Automated self-heal and pruning are
enabled for this disposable monitoring subtree so stale hashed ConfigMaps are removed; the
Namespace is explicitly protected from prune and the manual Grafana Secret is not Argo-managed.

### D5 — Manual Secret boundary

The script provisions `monitoring/grafana-admin` only in explicit apply mode. It reads a secure
password, does not print it, and never writes it to Git or a generated workspace file.

## Validation Strategy

1. Parse PowerShell and dashboard JSON; run feature static assertions.
2. Run `kubectl kustomize infra/monitoring` and client-side dry-run.
3. Run the Phase 25 script without `-Apply` and prove no live mutation occurs.
4. After merge, run with `-Apply`; wait for Argo `Synced/Healthy` and both rollouts.
5. Query Prometheus `/api/v1/targets` and require all eight jobs to be healthy.
6. Query Prometheus `/api/v1/rules` and require expected rule groups without errors.
7. Query Grafana health and dashboard search through a local port-forward.
8. Verify both monitoring Services remain ClusterIP and application Deployments remain available.

## Rollback

- Revert the source commit or suspend/delete only the `flash-sale-observability` Argo Application.
- Deleting monitoring resources does not delete application data or change the eight application
  Deployments.
- Metric history and local Grafana state are disposable by design; no database rollback is needed.
