# Data Model: Product Catalog Administration

Feature 010 reuses the Product catalog schema from Feature 008 and adds small product-service-owned
support tables for idempotency replay and privileged mutation audit. No table crosses a service
boundary.

## Existing Catalog Tables Reused

### `products`

Used as the Product aggregate root persistence table.

Relevant fields:

- `id`: Product identity.
- `code`: natural key, mutable only before the Product first becomes `ACTIVE`.
- `slug`: public/admin URL identifier, mutable only before the Product first becomes `ACTIVE`.
- `name`, `short_description`, `description`, `attributes`: Product content.
- `status`: `DRAFT`, `ACTIVE`, `INACTIVE`, `ARCHIVED`.
- `published_at`: set when first published/reactivated according to contract behavior.
- `version`: Product aggregate optimistic-lock version.

Feature 010 must treat `ARCHIVED` as final and retained. No hard delete is introduced.

### `product_variants`

Used for Variant/SKU administration and base VND price.

Relevant fields:

- `id`: Variant identity.
- `product_id`: owning Product.
- `sku`: natural key, immutable after the owning Product first becomes `ACTIVE`.
- `barcode`: optional unique identifier.
- `name`, `attributes`, `weight_grams`, `sort_order`: admin-maintained metadata.
- `base_price`, `currency`: non-negative VND Money.
- `status`: `ACTIVE`, `INACTIVE`, `ARCHIVED`.
- `version`: Variant row version; Product aggregate version remains the expected-version boundary
  for admin commands.

### `product_categories`

Used for Product memberships to existing Categories only.

Relevant fields:

- `product_id`, `category_id`: composite identity.
- `is_primary`: at most one primary Category per Product.
- `sort_order`: display order.

Feature 010 does not create, re-parent, archive, or delete Category hierarchy records.

### `product_media`

Used for URL metadata only.

Relevant fields:

- `id`: media identity.
- `product_id`: owning Product.
- `variant_id`: optional Variant owned by the same Product.
- `media_type`: `IMAGE` or `VIDEO`.
- `url`, `alt_text`, `mime_type`, `width_px`, `height_px`, `file_size_bytes`: metadata.
- `sort_order`, `status`: admin-maintained display state.

Binary upload, CDN processing, image resizing, and transcoding are out of scope.

## New Table: `product_admin_idempotency_keys`

Stores replayable outcomes for create and lifecycle commands.

| Column | Type | Null | Rules |
|--------|------|------|-------|
| `id` | `UUID` | No | Primary key, generated by database |
| `actor_id` | `VARCHAR(128)` | No | Authenticated admin actor identity |
| `idempotency_key` | `VARCHAR(128)` | No | Client-provided key |
| `command_name` | `VARCHAR(80)` | No | Stable command identifier such as `CREATE_PRODUCT_DRAFT` |
| `request_hash` | `VARCHAR(128)` | No | Hash of canonical command payload and command name |
| `target_product_id` | `UUID` | Yes | Product target when known |
| `http_status` | `INTEGER` | No | Stored replay status |
| `response_body` | `JSONB` | No | Stored response body for replay; must be a JSON object |
| `created_at` | `TIMESTAMPTZ` | No | Creation time |
| `completed_at` | `TIMESTAMPTZ` | No | Time original command completed |
| `expires_at` | `TIMESTAMPTZ` | No | `created_at + 7 days`; replay allowed only before this instant |

Indexes and constraints:

- Unique `(actor_id, idempotency_key)`.
- Index `(expires_at)` for cleanup.
- Check non-blank `actor_id`, `idempotency_key`, `command_name`, and `request_hash`.
- Check `http_status` between 100 and 599.
- Check `expires_at > created_at`.

Behavior:

- Same actor/key/request hash before `expires_at`: replay original `http_status` and `response_body`.
- Same actor/key with a different request hash before `expires_at`: reject as idempotency conflict.
- At or after `expires_at`, the stored outcome is not replayable and the same actor may reuse the key
  for a fresh command. The persistence adapter atomically removes or replaces the expired replay row
  before claiming the existing unique `(actor_id, idempotency_key)` slot. Normal command validation
  and conflict rules apply; rows in `product_admin_audit_logs` are retained independently.
- Cleanup can be opportunistic or scheduled in product-service.

## New Table: `product_admin_audit_logs`

Stores privileged mutation outcomes for product-service audit evidence.

| Column | Type | Null | Rules |
|--------|------|------|-------|
| `id` | `UUID` | No | Primary key, generated by database |
| `actor_id` | `VARCHAR(128)` | No | Authenticated admin actor identity |
| `trace_id` | `VARCHAR(128)` | No | Runtime trace/correlation identity |
| `command_name` | `VARCHAR(80)` | No | Stable command identifier |
| `target_product_id` | `UUID` | Yes | Product target when known |
| `outcome` | `VARCHAR(30)` | No | `SUCCESS`, `REPLAYED`, `REJECTED`, or `CONFLICT` |
| `error_code` | `VARCHAR(80)` | Yes | Stable error code for rejected/conflict outcomes |
| `product_version` | `BIGINT` | Yes | Resulting or conflicting Product version when available |
| `created_at` | `TIMESTAMPTZ` | No | Audit event time |

Indexes and constraints:

- Index `(target_product_id, created_at DESC)`.
- Index `(actor_id, created_at DESC)`.
- Index `(trace_id)`.
- Check non-blank actor, trace, command, outcome, and error code when present.
- Check outcome in the approved set.
- Check `product_version IS NULL OR product_version >= 0`.

Audit logs are service-owned and do not replace centralized log aggregation or tracing.

## Product Lifecycle

```text
DRAFT -> ACTIVE
ACTIVE -> INACTIVE
INACTIVE -> ACTIVE
DRAFT|ACTIVE|INACTIVE -> ARCHIVED
ARCHIVED -> final retained state
```

Publication/reactivation prerequisites:

- Product has required content.
- Product has at least one active Variant.
- At least one active Variant has valid non-negative VND base price.

Non-prerequisites:

- Category status.
- Media presence.
- Campaign/flash-sale price.
- Stock availability.

## Concurrency Model

- Product aggregate expected version comes from `products.version`.
- Update and lifecycle commands include expected Product version.
- Stale expected version returns conflict and persists no mutation.
- Multi-part composition commands are atomic all-or-nothing.
