# Research: Product Catalog Schema

## Decision 1: Start with five Product-owned tables

**Decision**: Create `categories`, `products`, `product_variants`, `product_categories`, and `product_media` only.

**Rationale**: These tables cover the minimum useful catalog, SKU, categorization, and gallery foundation while preserving Product ownership. They match the reviewed design and do not pre-implement another bounded context.

**Alternatives considered**: A Brand table was deferred because no brand-management behavior is approved. Inventory, campaign price, Cart, Order, and Outbox tables were rejected because they belong to other contexts or later event features.

## Decision 2: Use UUID identifiers generated by PostgreSQL

**Decision**: Use `UUID` primary keys with `gen_random_uuid()` defaults.

**Rationale**: Product identifiers can be created independently without exposing insertion order and can later travel safely through contracts/events. PostgreSQL 17 provides the required function in the selected local target.

**Alternatives considered**: Identity integers are simpler and smaller but make distributed identifier generation and future contract use less convenient. ULID would require an additional generation convention or extension not yet approved.

## Decision 3: Keep Money on Product Variant

**Decision**: Store `base_price NUMERIC(19,4)` and `currency CHAR(3)` together on each variant, enforce non-negative amount, and initially accept only `VND`.

**Rationale**: Amount and currency form one Money value. Moving currency to Product would let changing one row reinterpret every existing variant amount without conversion. Repeating three currency characters is negligible compared with the integrity benefit.

**Alternatives considered**: Product-level currency was rejected for split Money integrity. A `variant_prices` multi-market table was deferred until market, validity, and pricing behavior are specified.

## Decision 4: Preserve initial lifecycle and flexible catalog metadata

**Decision**: Include category hierarchy, documented status fields, Product publication time, and object-shaped JSON attributes for Product and Variant.

**Rationale**: These are part of the already discussed initial Product design and prevent the first Product API from immediately requiring a breaking table rewrite. Database checks constrain statuses and JSON shape while leaving detailed attribute semantics to future domain features.

**Alternatives considered**: A very small name/slug-only schema was rejected as insufficient for the requested initial catalog. Dedicated attribute-definition tables were deferred because attribute querying and validation behavior are not approved.

## Decision 5: Use deterministic, query-shaped indexes only

**Decision**: Use `(category_id, sort_order, product_id)` for category browsing, plus small owner/order indexes for category hierarchy, variants, media, and Product publication.

**Rationale**: The reviewed index order supports category filtering, deterministic ordering, joins, and keyset pagination. Placing boolean `is_primary` between category and order would break the general category ordering path.

**Alternatives considered**: `(category_id, is_primary, sort_order)` was rejected. A primary-membership partial browse index was deferred until a query proves it necessary. A partial unique index is still used solely to enforce at most one primary category per Product.

## Decision 6: Enforce Product/Variant media ownership with a composite FK

**Decision**: Add unique `(product_id, id)` on variants and reference it from media `(product_id, variant_id)` while retaining a direct Product FK.

**Rationale**: Product-level media may have a null variant. For variant media, the database must reject a Variant belonging to a different Product.

**Alternatives considered**: Separate independent Product and Variant FKs would allow mismatched ownership. An application-only check was rejected because imports and future adapters could bypass it.

## Decision 7: Use PostgreSQL formatted SQL behind an explicit YAML include

**Decision**: Keep the master changelog in YAML and implement the first changeset as formatted SQL.

**Rationale**: JSONB defaults/checks, partial unique indexes, UUID defaults, ordered indexes, and explicit named constraints are clearer and easier to review in PostgreSQL SQL. The explicit master include preserves stable execution order.

**Alternatives considered**: Pure YAML was possible but would mix raw SQL fragments for PostgreSQL-specific checks/indexes. `includeAll` was rejected because filesystem ordering is an unnecessary source of migration ambiguity.

## Decision 8: Add JDBC, not JPA

**Decision**: Add Spring JDBC/Hikari and the PostgreSQL runtime driver; do not add Spring Data JPA.

**Rationale**: Liquibase requires a datasource, but this feature defines no entity or repository. Adding JPA would imply an unapproved persistence adapter and mapping model.

**Alternatives considered**: JPA was deferred to the first Product persistence/use-case feature. A migration-only external CLI would avoid runtime datasource support but would make the service unable to own/run the established Spring Boot migration path.

## Decision 9: Separate fast smoke tests from real migration tests

**Decision**: Keep `ProductServiceApplicationTests` database-independent and add opt-in Failsafe `ProductMigrationIT` with PostgreSQL Testcontainers.

**Rationale**: Normal module/full builds remain fast and do not require Docker, while the immutable first changeset still receives real PostgreSQL constraint and idempotency coverage.

**Alternatives considered**: H2 was rejected because it cannot faithfully validate PostgreSQL JSONB, partial indexes, UUID defaults, and catalog behavior. Requiring Docker for every context test was rejected as unnecessary coupling.

## Decision 10: Run local migration as an explicit one-off process

**Decision**: Normal Product replicas keep Liquibase disabled; Compose supplies the datasource, and developers enable Liquibase only in a one-off non-web Product process.

**Rationale**: This matches the documented future Kubernetes Job model, makes migration execution visible, and avoids multiple replicas racing during deployment. The user-requested local database is still migrated explicitly in this feature.

**Alternatives considered**: Enabling Liquibase on every Product container startup is convenient but less representative of the planned production model. Deleting the PostgreSQL volume to rerun bootstrap was rejected as destructive.
